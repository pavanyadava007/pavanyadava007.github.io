## Problem & constraints

Silicon validation labs already have an anomaly detector: the spec limit. Any proposal to replace
it with machine learning has to answer one question before any other - does it catch failures the
limit screen misses, on a split that cannot leak?

That constraint is the whole design. Test measurements from the same die are highly correlated, so
a random row split will happily report a beautiful F1 that means nothing. The split here is
**grouped by device serial**: no die appears on both sides. Everything downstream is only as
credible as that grouping.

The second constraint is that an agent with database access in a validation lab is a liability
unless it is boxed in. All 14 tools are read-only, guarded at the SQL layer, and logged, and CI
runs the suite against both SQLite and a live PostgreSQL so the guard is tested where it will run.

## Results

On the DUT-grouped hold-out the supervised Random Forest reaches **F1 0.900 with ROC-AUC 0.963**,
against the spec-limit screen's **F1 0.531**. The concrete version of that number is more useful
than the number: **14 escapes** - real defects that passed every spec limit - and **3 overkills**,
healthy parts the limit screen wrongly failed.

The agent side turns 240 runs and 92,160 measurements into reports, block diagrams and AEC-Q100
test plans on request, with 97 tests and a ruff-clean, typed 6.1k LOC codebase behind it.

## Ablations

Five detectors were compared on the same grouped split. The result worth reporting is the one that
went the wrong way: the **rank-fused ensemble scored 0.816**, below the supervised model's 0.900.
Rank averaging pulls a strong learner toward two weaker ones, and a fusion that is only defensible
as "ensembles are usually better" is not defensible.

Fusion is kept in the codebase for one specific case and labelled as such - the cold start, where
a new product has no failure-analysis labels at all and a supervised model cannot be trained yet.
